*March 2025 — implementation notes updated November 2026*

CI orchestration must coordinate processes that can fail independently: repository checkout, containers, reporting APIs, and cleanup. TemporalCI is a proof of concept exploring whether Temporal's persisted workflow history makes those decisions easier to inspect and manage.

## The Insight

[Temporal](https://temporal.io/) is a durable execution platform. It was built so that long-running processes — order fulfillment, payment processing, data pipelines — can survive infrastructure failures and resume exactly where they left off.

A CI pipeline is just another long-running process:

1. Clone a repo
2. Run some commands in containers
3. Report results

Each of those steps is an **activity** in Temporal's model. Temporal can replay orchestration decisions using recorded activity results. Whether a failed activity runs again depends on its retry policy.

TemporalCI passes a worker-local checkout path between activities. A replacement worker may not have that directory, and ordinary build steps currently have one attempt. Workflow replay therefore does not guarantee recovery of the build process or its filesystem.

## What Temporal Contributes

Temporal supplies workflow history, task queues, and configurable activity policies. The application still has to handle external side effects, credentials, and cleanup.

### Automatic Retries with Backoff

Each activity has its own retry policy. Clone has at most three total attempts, including the initial attempt. Regular build steps have one total attempt and are not automatically retried.

```go
// Clone gets at most 3 total attempts.
cloneOpts := workflow.ActivityOptions{
    RetryPolicy: &temporal.RetryPolicy{
        MaximumAttempts: 3,
        InitialInterval: 5 * time.Second,
        BackoffCoefficient: 2.0,
        MaximumInterval: 30 * time.Second,
    },
}

// Build steps get 1 total attempt: no automatic retry.
stepOpts := workflow.ActivityOptions{
    RetryPolicy: &temporal.RetryPolicy{
        MaximumAttempts: 1,
    },
}
```

### Graceful Cancellation

When a new push arrives for the same branch and event/pipeline, TemporalCI requests cancellation of the previous workflow and attempts cleanup:

1. Cancel running activities
2. Delete orphaned K8s pods
3. Report the final status to GitHub

Cleanup uses a **disconnected context** so it can be attempted after workflow cancellation. It remains best effort. Cancellation is cooperative and does not prove every shell subprocess or pod has stopped; verify termination before retrying infrastructure operations.

### Execution History

Every workflow execution is recorded. You can:

- See the exact input and output of every activity
- See how long each step took
- Inspect recorded events to debug orchestration failures
- Query running workflows for real-time status

The Temporal Web UI displays workflow history. It does not replace build-log storage or infrastructure monitoring. Activity payloads may contain credentials in this POC, so protect Temporal and its database.

<Aside type="tip">
With GitHub reporting configured and a real pull-request event, result comments can link developers to the workflow. The signed local test event does not demonstrate PR reporting.
</Aside>

## Why Not Just Use Temporal Directly?

You could write Temporal workflows for CI yourself. TemporalCI is the opinionated layer on top:

- **`.temporalci/*.yaml`** — declare named pipelines without writing Go workflows
- **GitHub integration** — webhook handling, commit status, PR comments with logs
- **K8s pod execution** — Kubernetes steps run in separate pods with resource limits
- **Helm chart** — local and EKS examples need environment-specific secrets and configuration
- **Security controls** — operator authentication and optional network policies; policies are disabled by default and require an enforcing CNI

## The Trade-offs

The current POC is useful for evaluating workflow orchestration, not for a production reliability or tenant-isolation guarantee.

**Useful experiments:**
- Trusted Go, container, and infrastructure workloads
- Workflow history and per-activity retry policies
- Kubernetes build execution in disposable infrastructure

**Open limitations:**
- Worker-local checkout state during restarts
- Credentials in activity history
- Best-effort cancellation and cleanup
- Unisolated local command fallback when no in-cluster Kubernetes client is available
