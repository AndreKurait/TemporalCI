Build TemporalCI locally and explore a CI pipeline in a disposable environment. This is a proof of concept for repositories you trust.

## Prerequisites

Before you start, make sure you have:

- [minikube](https://minikube.sigs.k8s.io/docs/start/) (v1.32+)
- [Helm 3](https://helm.sh/docs/intro/install/) (v3.14+)
- [kubectl](https://kubernetes.io/docs/tasks/tools/)
- Docker and OpenSSL
- A public GitHub repo you control to test with

<Aside type="tip">
No AWS account needed. Everything runs locally on minikube.
</Aside>

## Install TemporalCI

<Steps>

1. **Clone the TemporalCI repo**

   ```bash
   git clone https://github.com/AndreKurait/TemporalCI.git
   cd TemporalCI
   ```

2. **Build and start the local stack**

   ```bash
   ./scripts/local-up.sh
   ```

   The script builds and loads the image, registers Helm repositories, creates fresh development secrets when absent, and installs into the `temporalci` namespace. A new cluster defaults to 8 CPUs and 16 GiB RAM; see the [local development guide](/TemporalCI/getting-started/local-dev/) to customize it.

3. **Inspect readiness**

   ```bash
   kubectl get pods -n temporalci
   ```

   Startup time depends on downloads and cluster resources. The local setup deliberately leaves GitHub API credentials empty; add scoped credentials only if you need remote status reporting.

</Steps>

## Add a Pipeline to Your Repo

Create `.temporalci/default.yaml` in your repository root:

<Tabs>
  <TabItem label="Go">
```yaml
steps:
  - name: build
    image: golang:1.26
    command: go build ./...
    timeout: 5m

  - name: test
    image: golang:1.26
    command: go test -v ./...
    timeout: 5m
    depends_on: [build]

  - name: vet
    image: golang:1.26
    command: go vet ./...
    depends_on: [build]
```
  </TabItem>
  <TabItem label="Node.js">
```yaml
steps:
  - name: install
    image: node:24
    command: npm ci

  - name: test
    image: node:24
    command: npm ci && npm test
    depends_on: [install]

  - name: build
    image: node:24
    command: npm ci && npm run build
    depends_on: [install]
```
  </TabItem>
  <TabItem label="Python">
```yaml
steps:
  - name: install
    image: python:3.12
    command: pip install -r requirements.txt

  - name: test
    image: python:3.12
    command: pip install -r requirements.txt pytest && python -m pytest
    depends_on: [install]

  - name: lint
    image: python:3.12
    command: pip install ruff && ruff check .
    depends_on: [install]
```
  </TabItem>
</Tabs>

Each Kubernetes step gets a fresh checkout. Install its dependencies in that step; `depends_on` controls ordering and success conditions, and does not share the previous container filesystem.

From your test repository's checkout, commit and push the pipeline so the worker can fetch it:

```bash
git add .temporalci/default.yaml
git commit -m "Add a TemporalCI pipeline"
git push origin HEAD
```

The trigger example below uses `main`. Replace it with the branch you just pushed if different. Uncommitted or unpushed files are not included in the worker's clone.

## Connect GitHub

Start with a signed local test request:

<Steps>

1. **Forward the webhook server to loopback**:

   ```bash
   kubectl port-forward svc/temporalci-webhook -n temporalci 8080:8080
   ```

2. **Send a signed event in another terminal**:

   ```bash
   ./scripts/local-trigger.sh your-org/your-repo main
   ```

   The helper reads the generated local webhook secret and signs the payload. An accepted signed GitHub event registers the repository automatically. Manual management APIs require an allowed OAuth operator.

</Steps>

## Trigger a Build

The local test event asks TemporalCI to:

1. Receive the webhook event
2. Start a Temporal workflow
3. Clone your repo and read `.temporalci/default.yaml`
4. Run each step as an isolated K8s pod
5. Attempt GitHub reporting if credentials are configured

For real GitHub deliveries, configure an HTTPS webhook endpoint and the matching secret through your own deployment. A localhost port-forward is not reachable by GitHub. Review the [security model](/TemporalCI/concepts/security/) before accepting pull-request builds.

Inspect this local run in the Temporal Web UI below. The synthetic push is not a pull-request event and does not supply a commit SHA, so it does not demonstrate PR comments or commit status reporting. Those require a real event with the corresponding metadata and scoped GitHub credentials.

## View the Temporal Web UI

```bash
kubectl port-forward svc/temporalci-web -n temporalci 8088:8080
```

Open [http://localhost:8088](http://localhost:8088) to see your workflow executions, activity details, and timing.

## What Happens Under the Hood

```
git push → GitHub Webhook → Webhook Server → Temporal Workflow
                                                    │
                                              ┌─────┴─────┐
                                              │  CloneRepo │
                                              └─────┬─────┘
                                              ┌─────┴─────┐
                                              │ RunStep   │
                                              │ build     │
                                              │ test      │
                                              │ vet       │
                                              └─────┬─────┘
                                            ┌───────┴───────┐
                                            │ ReportResults │
                                            └───────────────┘
```

Temporal can replay workflow decisions after a worker restart. Worker-local checkout files and running commands are not preserved by replay, and regular build steps currently have one attempt. Treat restart recovery as an area to evaluate in this POC, not a build-survival guarantee.
